# L3 Prototype Implementation Plan

## Goal and boundary

Extend the reviewed L2 approval workflow into a repeatable, auditable **local prototype**. Demonstrate an email-to-verified-install lifecycle and a cited policy assistant using fixtures and faithful deployment simulation. Do not connect to real mailboxes, employee directories, license systems, endpoint management, or production deployment services. An accepted deployment job must remain distinct from verified installation; only simulated verification success closes a request.

## What L2 already provides

Retain L2's requester identity checks, ordered human approvals, rejection handling, reminder/escalation behavior, audit history, duplicate-request guard, and decision authorization. The current app accepts interactive requests, stores workflows in a process-local dictionary, and ends at `approved`; it does not provide email intake, entitlement/device/package checks, deployment, installation verification, or policy Q&A. L2 tests use `unittest` and stub agent calls, making them a useful regression base.

## Prototype structure

Keep the L2 implementation intact and place L3 additions under this directory:

- `intake.py`: parse fixture email events, validate sender identity, collect missing fields through simulated replies, and associate authorized replies with the original request. `main.py` option 6 runs the inbox/outbox simulation from `fixtures/inbound_emails.json`; no live email account is required.
- `service.py`: orchestrate eligibility, entitlement, device readiness, budget, existing approval, deployment, verification, and closure transitions.
- `adapters/`: deterministic in-memory or JSON-backed simulators for email, employee/device/license/package data, deployment job acceptance, and installation results. Give events stable IDs and deduplicate before side effects.
- `installation/`: a separate memory store, Agent tools/prompts, and a secondary scheduler that hands fully approved requests to the Agent for the next installation action.
- `fixtures/employee_devices.json` and `fixtures/approved_software.json`: ten employee-assigned device profiles and synthetic approved package/version records. The catalog's highest-ranked compatible approved version is the latest version for this prototype.
- `policy/`: ingest versioned policy sections into ChromaDB and retrieve the exact approval cost tier only when a new request is ready for routing. `policy_documents/` contains the L2-derived prototype corpus.
- `tests/` and `fixtures/`: repeatable scenario tests and synthetic emails, policies, devices, packages, and deployment outcomes.
- `evidence/`: workflow run records, policy evaluation cases/results, operating notes, limitations, ownership checklist, and rollout recommendation.

Use a small persistent local store (SQLite is sufficient) for request state, idempotency keys, and append-only event history so a restart does not lose the prototype's audit trail. Use the user's ChromaDB server for policy passages, not SQLite. Keep integration boundaries behind adapter interfaces. Adapt L2 through a narrow service seam rather than copying its approval rules; ensure L2 modules can be imported consistently from tests and the L3 entry point.

## Policy assistant: ChromaDB-backed RAG

Connect with ChromaDB's Python HTTP client using `host="localhost"`, `port=8000`, `tenant="default_tenant"`, and `database="default_database"`. The ingestion entry point is `L3/policy/ingest_chroma.py`; run it from `L3/` with `python -m policy.ingest_chroma`. It reads sectioned Markdown files from `L3/policy_documents/`, uses stable IDs and upsert for repeatable ingestion, and keeps collection connection values configurable through environment variables. Install dependencies from the repository root with `python -m pip install -r requirements.txt`; verify installed client/server compatibility when setting up the prototype.

Use the dedicated `assetdesk_policy` collection. Each stored record is a coherent policy section with a stable ID, text, and scalar metadata for `document_id`, `document_title`, `version`, `section_id`, `section_title`, `effective_date`, `approval_status`, `authority`, and source file. The initial documents in `L3/policy_documents/` are extracted from L2 implementation and marked `unverified`; they may be indexed for prototype evaluation but must not be presented as current authoritative company policy. Before real employee guidance, ingest supplied company documents with explicit current/approved status and filter retrieval to that approved set. Preserve historical versions for audit and never treat an older passage as current just because it scores highly. Keep source files and ownership metadata outside Chroma as well.

For each new request, validate the input and duplicate status first, then retrieve exactly one cost-tier record from Chroma using the amount in cents and numeric range metadata. Pass that policy text, roles, version, and citation into the approval-routing LLM prompt. The routing LLM may use the existing in-memory employee and role-holder tools, but it must not call Chroma or a local policy tool. Validate the returned approver chain against the roles in the retrieved record and the employee directory. Record the Chroma record ID and citation in workflow history. If Chroma is unavailable or no unique tier is returned, stop request creation and surface an error; never fall back to the hard-coded L2 threshold function. Do not call Chroma for approval decisions, installation scheduling, IT pending, or other flows; those use the existing in-memory state and tools.

Choose and configure the embedding and generation providers before implementation. Prefer a reproducible local embedding setup for the prototype if available; otherwise document required network access and credentials. Keep model names and thresholds configurable, never commit credentials, and ensure the same embedding configuration is used at index and query time. The user's supplied current policy corpus and section structure are still required; until provided, use labeled synthetic documents strictly for demonstration.

## Implementation sequence

1. **Freeze the L2 baseline.** Run `cd L2 && python -m unittest discover -s tests -v`; record current behavior and define a versioned request/event schema. Preserve L2 tests and its `approved` meaning.
2. **Add durable request intake.** Simulate inbound email and acknowledgement. Create one request per new message, deduplicate by provider message ID, validate sender against employee records, request missing details, and attach only authenticated/authorized replies to the same request. Expose request ID, status, owner, next action, and history in a simple CLI/report.
3. **Add prerequisite gates.** Check software eligibility, license availability, registered device ownership/readiness, package approval/version, and budget before deployment. Route policy-defined human decisions through L2's ordered chain. Missing/failed checks block with a named owner and next action; silence only reminds/escalates.
4. **Add simulated delivery and verification.** A secondary scheduler discovers approval workflows whose entire approval chain is approved and copies them to separate installation memory. It invokes the installation Agent with the approval list and tools. The Agent decides whether to wait for a device, choose the latest compatible approved version, add missing software to the IT pending list, queue a user-scope job, simulate installation, or verify the result. Tools enforce completed approvals, assigned-device ownership, latest-version selection, user scope, and no-admin requirements. The scheduler does not choose the workflow transition. Catalog changes are reloaded on each scheduler cycle so the Agent can resume an IT-pending request when a version becomes available. Close only after the Agent invokes verification and the checks pass; failures/unverified results stay open.
5. **Harden replay behavior and audit.** Make intake, replies, decisions, jobs, results, reminders, and completion messages idempotent. Authorize every state-changing event, retain actor/source/time/result, and test duplicate and out-of-order delivery.
6. **Build and evaluate request-time policy retrieval.** Connect to the configured ChromaDB tenant/database and upsert the versioned policy sections plus structured cost-tier records. Exercise all tier boundaries and confirm the routing LLM receives the retrieved policy before it runs. Confirm duplicate/invalid requests and non-request workflows do not access Chroma, and Chroma failures stop request creation without a local fallback.
7. **Package the handover.** Document local setup, demo commands, fixture reset/replay, workflow evidence, policy evaluation, known limits, accountable owners, required real-company configuration, and a recommendation for or against a later rollout.

## Acceptance evidence

The prototype is ready for review when a clean fixture run demonstrates: a new email creates one tracked request and acknowledgement; missing details and a reply update that same request; authorization and prerequisites control ordered approval; silence cannot approve; duplicate events do not repeat business actions; the secondary scheduler hands only fully approved requests to the Agent; the Agent selects the latest approved compatible version or records missing software in the IT pending list; an IT catalog update causes the Agent to resume; user-scope install simulation requires no admin rights; accepted deployment alone does not close; offline, unavailable-package, failed, and unverified cases remain open; only a matching verified installation closes and sends one completion message. A report should show status, owner, next action, and timestamped history for each scenario. Policy evidence must show successful Chroma connection with the configured tenant/database, that only current approved records were retrieved, all required case categories, citation validation/refusals, and baseline versus improved results.

## Assumptions and handover dependencies

Until current company materials and named owners are supplied, use clearly labeled synthetic policies and fixtures; do not invent policy answers. The handover must identify the real sources and owners needed for employee identities, authorized email senders, software eligibility, budget thresholds, license inventory, device registration/readiness, approved packages/versions, deployment and verification services, and policy document maintenance. No production rollout should be inferred from a successful simulation.
